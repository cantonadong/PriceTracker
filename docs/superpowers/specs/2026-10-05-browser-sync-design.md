# 监控列表浏览器同步设计

## 目标与范围

用户希望在多台电脑上通过浏览器账号同步监控列表，保留目标价格、自定义标题和排序。现有监控仍能离线使用。继续直接在 main 上工作，不运行测试；交付可加载的浏览器扩展，不生成 EXE。本次不自动推送或创建新 Release。

同步：商品 ID、链接、标题及 customTitle 标记、CSS 价格选择器、目标价格、通知开关、创建时间，以及完整列表顺序。删除操作也同步。

不同步：当前价格、币种、价格文本、更新时间、刷新成功时间、错误状态、已达目标和通知触发时间。各设备自己刷新价格、计算状态。搜索词和已达目标筛选保留为页面临时状态。

新设备收到的商品，在本机取得价格之前显示“—”，不显示已达目标，不发送到价通知；不能把 null 转成 0 判断价格。此规则同时覆盖列表、弹窗、徽标、编辑目标价和后台提醒。

## 方案选择

1. 整个 watches 数组改用 storage.sync：改动小，但易超过单项配额，价格刷新也产生频繁上传，多设备会覆盖整份列表。不采用。
2. 本地列表加按商品拆分的同步记录：保留本地价格缓存，用户编辑通过后台统一写入，支持离线队列和冲突合并。采用。
3. 自建云端服务：可突破浏览器配额，但需要服务和登录，不属于本次范围。

## 数据与冲突规则

- 新增 watch-store.js，作为后台统一存储入口。页面和 picker 通过 runtime 消息提交新增、改名、改目标价、排序、删除；读取仍可使用本地 watches 投影。
- 每个商品一个同步键 pt:watch:<id>，格式包含 schemaVersion、配置数据及各配置组的版本标记。版本为混合逻辑时间（毫秒、逻辑计数、设备 UUID），比较结果确定且不依赖价格更新时间。
- 标题与 customTitle 作为一个配置组，链接与 selector 作为一个配置组；目标价、通知开关各自为组。不同组并行编辑可以合并，同一组采用较新版本。收到远端版本后推进本地逻辑时钟。
- 排序使用独立 pt:order 键，包含 IDs 与版本，采用较新顺序。删除的 ID 忽略；未列入的新商品按创建时间及 ID 稳定补入。排序记录超过单项配额时提示失败，不截断。
- 删除写入该商品键的墓碑，墓碑对同一商品 ID 的配置更新具有优先权，防止离线设备恢复已删除商品。删除后重新添加生成新 ID。墓碑暂不自动清理；接近配额时显示容量提示。
- 只写变化的商品记录及顺序，不在每次价格刷新时重新上传配置。不以空数组或不完整远端读取结果清空已有列表。
- 后台合并数据后重建本地 watches，保留相同 ID 的本机价格缓存。链接或选择器变化时清除对应价格缓存。不会覆盖正在输入的标题草稿。
- 配置修改和刷新结果的最终提交通过同一后台串行队列执行；网络抓价在队列外进行，返回后重新读取并核对链接、选择器及请求版本，避免旧请求覆盖新配置。

## 初始化与离线写入

初始化先读取本地快照、持久待上传记录和 sync 全部相关键，再合并并生成本地投影。已迁移设备不得再次把旧本地快照当成全新修改发布。

首次迁移保留现有 ID、标题、顺序和本机价格缓存，为尚无同步版本的配置生成初始版本。远端墓碑优先；已有远端配置优先于未版本化的同 ID 本地配置。各设备既有列表包含不同 ID 时合并保留，不按 URL 自动删重，避免误删同链接不同监控。

本地编辑先持久保存配置、版本和待上传队列，再返回成功。后台批量上传合并短时间连续操作，失败保留队列；通过 Chrome alarm、启动及后续编辑重试，使用退避，不依赖 service worker 内存定时器。远端变化仅在合并结果确实不同时回写，防止循环。

旧的一次性价格排序迁移标记在初始化投影时设为完成，避免新设备把同步来的手工顺序重置。自动排序按钮仍显式覆盖手工顺序并同步。

## 配额与用户提示

Chrome storage.sync 总量约 100 KB，单项 8 KB，并有键数和写入频率限制。写入前按 UTF-8 键与 JSON 长度核算，并以实际 API 错误为最终依据。不得静默删商品、截断标题或丢弃墓碑来腾出空间。

设置页底部显示“浏览器同步：已写入浏览器同步存储 / 有更改待写入 / 写入失败（原因）”。此状态只代表扩展写入状态，不声称云端或另一设备已经收到；API 无法可靠报告账号登录、同步开关和云端上传完成状态。

用户保存仍使用现有 toast；同步失败补充提示“已保存在本机，同步待重试”。不阻断监控、离线编辑或价格刷新。

## 固定扩展 ID 与旧数据迁移

当前 manifest 没有 key。为保证各电脑解压到不同目录时仍使用相同 ID，最终同步版加入固定公开 key；私钥不进入仓库。若存在该扩展原有发行公钥，优先复用；否则生成并固定新的公钥。

新增 key 可能改变目前解压版的 ID，新 ID 无法直接读取旧 ID 的本地存储。因此先提供不更改 ID 的迁移准备版本，增加列表导出和导入功能。用户在旧 ID 下导出 JSON，再安装固定 ID 同步版并导入；确认数据迁移完成后再停用旧版。不得修改正在使用的目录后要求用户去已消失的旧 ID 导出。

实现阶段保留可单独加载的“迁移准备版”ZIP（旧 ID、无 key）与“同步版”ZIP（固定 key）。准备版使用同一代码、仅打包时移除 key，必须在原安装目录更新后先导出。最终同步版正常包包含 key。文档明确两阶段步骤，不声称 ID 改变时能自动迁移。

导出仅由用户按钮触发，包含 schemaVersion、配置、顺序及可选本机价格快照；不包含凭据。导入验证结构、字段、大小和 URL 协议，通过后台存储入口合并，与同步墓碑规则一致；同 ID 导入不会意外恢复已删除监控。首次导入可保留本机快照，但后续本地刷新为准。

同一浏览器体系、同一同步账号、开启扩展数据同步及相同扩展 ID 是使用前提。Chrome 和 Edge 各自使用自己的同步服务，不保证二者互通；不保证解压扩展自动安装到其他电脑，另一电脑需要手动安装相同同步版。

## 文件与接口影响

- watch-store.js：初始化、配置版本、投影、串行提交、同步合并、离线待上传、配额和导入导出。
- background.js：接入存储入口，处理页面编辑和同步消息，配置变更与刷新结果合并，alarm 重试。
- dashboard.js/html/css：配置修改改走后台，增加同步状态、导出/导入，保留行内选字和编辑草稿。
- popup.js：保持本地读取，正确显示尚未刷新价格，自定义标题不做网页标题后缀清理。
- manifest.json：固定公开 key；现有 storage 和 alarms 权限足够，不增加云端服务。
- README.md：同步前提、配额、两阶段旧 ID 迁移和多电脑手动验收步骤。

## 验收与验证

不执行自动或手工测试。实施时检查代码差异、打包内容及固定 ID 计算，明确报告真实跨设备效果尚待用户验证。提供以下用户验收步骤：

1. 在旧 ID 下导出；安装固定 ID 版并导入，标题、目标价、顺序保留。
2. 同账号第二台电脑安装固定 ID 版，收到列表，未刷新价格显示“—”。
3. 修改标题、目标价、手工顺序与自动排序，另一设备最终一致。
4. 设备离线期间编辑，重连后合并；同商品不同配置组编辑均保留。
5. 删除商品，离线设备重连不恢复它；删除后新建监控正常同步。
6. 价格刷新只更新本机状态，不覆盖自定义标题和手工顺序。
7. 同步写入失败或超配额时本机数据保留，并出现明确提示。
